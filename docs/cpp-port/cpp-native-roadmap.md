# cpp-native Roadmap

## What this branch is

`cpp-native` is a restart of the QOM-replacement work, branched from commit
`0b475a32e2` — the last point where smoke tests passed 13/15. Everything
above that commit on `qom-replacement` (14 Option D Step 2 conversions,
including PCIDeviceClass, VirtioDeviceClass, I2C/SMBus/PMBus hierarchies)
is kept as a historical record on the old branch and is not carried
forward here.

## What we learned

See `qom-architecture-options.md` for the full analysis. The short version:

1. **Virtual methods on QOM class structs is a layout dead-end.** The C++
   Itanium ABI places the vtable pointer at offset 0 of any polymorphic
   class. QOM places `ObjectClass::type` at offset 0 of the same memory.
   They can't coexist. `qom_fixup_vtable<T>()` tries to paper over this
   by memcpy'ing a vtable pointer in after QOM sets up the class memory,
   but that memcpy lands on top of `ObjectClass::type` and corrupts it.

2. **QEMU device state structs are often embedded**, not only allocated
   via `qdev_new()`. Examples: `PL011State uart0;` inside
   `BCM2835PeripheralState`. This means the state struct's size and field
   layout are baked into other struct's layout. We can't freely rearrange
   fields or add a vtable pointer without breaking embedders.

3. **Phase 4 already found the right pattern.** Adding non-virtual C++
   methods to existing QOM state structs (as done in `pl011.h:65-92`) is
   clean, layout-preserving, and gives us C++ member-function syntax
   without vtables.

The mistake was Phase 5: reaching for `virtual` on class structs.
Non-virtual member functions were enough.

## The corrected design

**Core principle: zero vtables in device types.** No `virtual` keyword in
state structs or class structs. Use direct member functions, template
dispatch (CRTP where useful), and static function pointers populated from
member-pointer macros.

**What we delete, in priority order:**

| QOM artefact | Why it's waste | Replacement |
|---|---|---|
| `#ifdef __cplusplus` dual-view structs | Only existed to support virtual dispatch that didn't work | Single C++-native struct with non-virtual methods |
| `qom_fixup_vtable<T>()` | Layout-corrupting hack for a problem we now avoid | Deleted — never needed |
| `reinterpret_cast<Type*>(qom_ptr)` QOM macro casts | Runtime string-check for types the compiler already knows | `static_cast` or direct member access |
| Free `*_class_init` functions | 10-line boilerplate repeated 600× | `REGISTER_DEVICE(StateStruct, parent)` macro |
| `TypeInfo` struct literals | Boilerplate repeated 600× | Generated by the registration macro |
| `type_init(foo_register_types)` | Pairs with TypeInfo | Generated by the registration macro |
| `DEFINE_PROP_*` property macro forests | ~80 lines per complex device, member-offset brittle | `QEMU_PROP(&State::field, "name", default)` — compile-time checked |
| `VMStateDescription` compound literals | Hand-maintained list of field offsets | Member-pointer-based migration visitor |
| `OBJECT_DECLARE_TYPE` | Generates cast macros that do runtime string compare | Direct `static_cast` — the type is known statically |
| `DECLARE_INSTANCE_CHECKER` | Same | Same |

**What we keep, for now:**

- QOM's *runtime type registry* (`type_register_static`, `TypeImpl`,
  the hash table). This powers `-device pl011,...` string lookup and
  QMP introspection. It's ~500 lines and doing a real job.
- QOM's parent/child relationship tracking for property composition
  (`object_property_add_child`, bus attachment). Also doing a real job.
- The instance_init / realize / unrealize / reset lifecycle, because
  machine composition code depends on it.

Everything else is on the chopping block.

## Phase plan

### Phase 0 — Safety net (complete)

- [x] Branch from `0b475a32e2`
- [x] Verify smoke tests pass 13/15
- [x] Cherry-pick architecture analysis doc

### Phase 1 — Fix and simplify the CppDevice base classes

The existing `include/qom/cpp/object.h` and `include/qom/cpp/device.h`
have `virtual` methods in `CppDevice` that introduce a vtable. **These
base classes are currently broken and unused.** Rewrite them to be
zero-vtable helpers that provide:

- `static_cast`-based accessors (`deviceState()`, `sysBusDevice()`, etc.)
- No virtual methods at all
- Helper functions that wrap common QOM APIs (sysbus_init_mmio, etc.)

The `CppDevice` is a *view* over an already-allocated QOM object. It
contains no data members. Derived device classes contain their data
and define their methods directly, without C++ inheritance of
`CppDevice` (because inheritance with virtuals adds the vtable that
breaks everything). CppDevice is pure static utility.

### Phase 2 — `REGISTER_DEVICE` registration macro

Write a macro that takes a state struct + parent type + realize pointer
+ reset pointer and generates:

- The trampoline functions QOM needs (`static void X_cpp_realize(DeviceState*, Error**)`)
- The class_init function
- The TypeInfo struct
- The type_init registration

Before:
```cpp
static void pl011_realize(DeviceState *dev, Error **errp) { PL011State *s = PL011(dev); /* 30 lines */ }
static void pl011_reset(DeviceState *dev) { PL011State *s = PL011(dev); /* 10 lines */ }
static const Property pl011_properties[] = { /* ... */ };
static const VMStateDescription vmstate_pl011 = { /* ... */ };
static void pl011_class_init(ObjectClass *oc, const void *data)
{
    DeviceClass *dc = DEVICE_CLASS(oc);
    dc->realize = pl011_realize;
    device_class_set_legacy_reset(dc, pl011_reset);
    device_class_set_props(dc, pl011_properties);
    dc->vmsd = &vmstate_pl011;
    set_bit(DEVICE_CATEGORY_INPUT, dc->categories);
}
static const TypeInfo pl011_arm_info = {
    .name          = TYPE_PL011,
    .parent        = TYPE_SYS_BUS_DEVICE,
    .instance_size = sizeof(PL011State),
    .instance_init = pl011_init,
    .class_init    = pl011_class_init,
};
static void pl011_register_types(void) { type_register_static(&pl011_arm_info); /* etc */ }
type_init(pl011_register_types)
```

After (first target, preserving existing VMState and Properties):
```cpp
REGISTER_QEMU_DEVICE(PL011State, TYPE_PL011, TYPE_SYS_BUS_DEVICE,
    .realize = &PL011State::realize,
    .reset = &PL011State::reset,
    .init = &PL011State::init,
    .properties = pl011_properties,
    .vmstate = &vmstate_pl011,
    .categories = { DEVICE_CATEGORY_INPUT });
```

~60 lines → 7 lines. No new concepts, just boilerplate elimination.

### Phase 3 — Member-pointer property macros

Replace `DEFINE_PROP_*` with typed member-pointer versions:

Before:
```cpp
static const Property pl011_properties[] = {
    DEFINE_PROP_CHR("chardev", PL011State, chr),
    DEFINE_PROP_UINT32("clock-frequency", PL011State, clock_frequency, 24000000),
    DEFINE_PROP_BOOL("migrate-clk", PL011State, migrate_clk, true),
};
```

After:
```cpp
static const PropertyList pl011_properties =
    makeProperties<PL011State>(
        propChr    ("chardev",         &PL011State::chr),
        propUint32 ("clock-frequency", &PL011State::clock_frequency, 24000000),
        propBool   ("migrate-clk",     &PL011State::migrate_clk,     true));
```

Same line count, but the compiler verifies the member type matches the
property type at compile time. No more silent breakage when fields
change type. Underneath it still produces QEMU's `Property` array so the
rest of QOM works unchanged.

### Phase 4 — Member-pointer migration/VMState

Replace `VMStateDescription` hand-maintained field lists with a visitor
that walks member pointers:

Before:
```cpp
static const VMStateDescription vmstate_pl011 = {
    .name = "pl011",
    .version_id = 2,
    .minimum_version_id = 2,
    .post_load = pl011_post_load,
    .fields = (const VMStateField[]) {
        VMSTATE_UINT32(readbuff, PL011State),
        VMSTATE_UINT32(flags, PL011State),
        VMSTATE_UINT32(lcr, PL011State),
        /* 15 more fields */
        VMSTATE_END_OF_LIST()
    },
    .subsections = (const VMStateDescription * const []) {
        &vmstate_pl011_clock,
        NULL
    }
};
```

After:
```cpp
static const auto vmstate_pl011 = makeVmState<PL011State>("pl011", 2,
    vmField(&PL011State::readbuff),
    vmField(&PL011State::flags),
    vmField(&PL011State::lcr),
    /* 15 more */)
    .postLoad(&PL011State::postLoad)
    .subsection(vmstate_pl011_clock);
```

Produces the same `VMStateDescription` at compile time via `constexpr`.
On-wire format unchanged. Migration compatibility preserved.

### Phase 5 — Reference device port: PL011

Port `hw/char/pl011.cpp` to use all of the above. Target: ~450 lines
from ~735. Must boot `aarch64-softmmu virt` with serial output
identical to the current implementation.

### Phase 6 — Batch conversion

Once PL011 is proven, convert devices in priority order:

1. ARM virt machine devices (PL011, PL031, PL061, GPEX) — ~10 files
2. x86 q35 devices (serial, KBD/PS2, Q35/MCH, HPET, PCI host) — ~15 files
3. RISC-V virt devices (PLIC, ACLINT, APLIC, GPEX) — ~8 files
4. PPC pseries devices (spapr, VIO, XIVE) — ~15 files
5. Cross-platform VirtIO devices — ~25 files
6. Everything else that builds for the 5 targets — ~400 files

AI-driven, one-device-at-a-time, with smoke test as the oracle. Each
device conversion is a mechanical transformation of a known shape, so
it's template-generatable.

### Phase 7 — QOM infrastructure slim-down

Once ~all devices are converted:

- Delete `OBJECT_DECLARE_TYPE`, `OBJECT_DECLARE_SIMPLE_TYPE`,
  `DECLARE_INSTANCE_CHECKER` macros and their call sites
- Delete `OBJECT_CHECK`, `OBJECT_CLASS_CHECK`, `OBJECT_GET_CLASS` macros
  (all replaced by `static_cast` via the compile-time known types)
- Delete `DEFINE_PROP_*` macros (all replaced by member-pointer props)
- Delete `VMSTATE_*` macros (all replaced by member-pointer vmstate)
- Delete the cast cache in `ObjectClass` (no more runtime type checks)
- Delete `object_class_dynamic_cast_assert` (same)

What remains in `qom/object.cpp`: the registry hash, type_init ordering,
parent/child composition, property hash access for QMP. Probably
~400 lines down from the current ~2200. A thin facade over the C++
type system.

## Open questions

1. **Subclass overrides.** In the current design, a device subclass can
   override behavior via function pointers on the class struct. With
   zero-vtable C++, how do subclasses override? Options: (a) the
   subclass defines its own state struct that embeds the parent and
   provides its own realize (with QOM dispatching via function pointers
   on TypeInfo, like today); (b) function pointer table stored in class
   struct (`methods` sidecar, Option B from the analysis doc). Start
   with (a) because it's simplest.

2. **VirtIO device dispatch.** VirtIO devices currently use 25 function
   pointers on `VirtioDeviceClass`. The clean equivalent is a single
   struct of function pointers stored on the device, populated by the
   concrete subclass at realize time. Defer this — it's the hardest
   case and PL011 doesn't need it.

3. **`CppDevice` template or free functions?** The reinterpret_cast
   helpers (`deviceState()`, `sysBusDevice()`) are convenient but not
   essential. Could be plain functions taking the device pointer.
   Start as a namespace of free functions; add a CRTP base later only
   if the ergonomics demand it.

## Success criteria

- **Week 1:** Infrastructure (Phase 1-4) in place. PL011 (Phase 5)
  ported and booting `aarch64 virt` Debian netboot smoke test
  identically to master.
- **Week 2-3:** Top 100 most-used devices converted. Smoke tests stay
  at 13/15.
- **Week 4:** QOM infrastructure slimmed (Phase 7). Diff shows
  `qom/object.cpp` lost ~1500 lines and no device file grew.

## What this branch does NOT do

- Port the remaining 6 hard-blocked `.c` files to `.cpp`. Orthogonal
  and handled by the `qom-replacement` branch's existing plan.
- Rewrite TCG, coroutines, or other non-device subsystems. Scope is
  the device model only.
- Remove QOM's runtime type registry. Removed infrastructure items are
  only the ones made redundant by compile-time types; the runtime
  registry still serves `-device`, QMP, and hotplug.
